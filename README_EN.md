# Local LLM Token Usage Monitor Desktop

A lightweight desktop application for monitoring token usage and balances across multiple LLM providers. Built with Tauri, React, TypeScript, and Rust.

![License](https://img.shields.io/github/license/hajifish/Local-LLM-Token-Usage-Monitor-Desktop)

## Preview

![Preview](assets/screenshot-main.png)

## Features

- **Multi-Provider Support** — Monitor usage across multiple LLM platforms:
  - DeepSeek
  - Kimi (Moonshot)
  - Zhipu (GLM)
- **Real-Time Usage Tracking** — View token consumption and remaining balance at a glance
- **System Tray Integration** — Runs quietly in the background with a native tray icon
- **Auto-Start** — Optionally launch on system startup
- **Periodic Polling** — Automatically refreshes usage data on a configurable schedule
- **Low Resource Footprint** — Powered by Tauri's lightweight Rust backend

## Configuration & Key Security

The app stores each provider's API keys and other settings in a local configuration file. Starting with this release, that file has been upgraded from plain-text JSON to a **machine-bound encrypted envelope**. Please review the following before use.

### Configuration file location

| Platform | Path |
|----------|------|
| macOS | `~/Library/Application Support/com.hajifish.llm-token-monitor/config.json` |
| Windows | `%APPDATA%/com.hajifish.llm-token-monitor/config.json` |
| Linux | `~/.local/share/com.hajifish.llm-token-monitor/config.json` |

### The file is no longer editable plain text

The configuration file is now encrypted with XChaCha20-Poly1305. The key is derived via BLAKE3 from "this machine's hardware identifier + the app's built-in derivation context", and **the decryption key is never written to disk**. As a result:

- **Do not edit this file by hand** — its contents are ciphertext; editing it with a text editor is not only ineffective but may also render it undecryptable.
- Enter and change keys through the in-app **Settings page** (the Settings page still shows keys in plain text; the interaction is unchanged).
- On first launch of this release, the app automatically migrates any existing plain-text configuration to the encrypted format. The migration uses a "temporary file + atomic rename" with a read-back verification; if it fails, the original file is left untouched and retried on the next launch. After a successful migration, file permissions are tightened so that only the current user can read/write it (`0600` on Unix).

### Switching machines, reinstalling, or a changed system identifier

The encryption key is bound to this machine's hardware identifier. If you **switch computers, reinstall the OS, or the system identifier changes**, the existing ciphertext can no longer be decrypted. In that case:

- The app **will not silently overwrite** the original file. Instead, it backs the file up as `config.json.unreadable-<timestamp>.bak` and then lets you re-enter your keys.
- The frontend shows a banner informing you that the configuration file could not be read and needs to be filled in again.

### Version rollback warning

> **Important:** If you roll back to a version earlier than this upgrade, that older version cannot read the encrypted configuration file, and performing a save operation in it will overwrite the file in plain text — causing your saved encrypted keys to be lost. If you must roll back to an earlier version, record or export your keys from the Settings page first.

### Threat model (what it does and does not protect against)

We do not overstate our security guarantees. This scheme is designed to **significantly raise the cost of cracking the configuration file after it leaves this machine** — it is not absolute security:

- **It defends against** scenarios where a copy of the configuration file leaks passively after leaving this machine — for example via cloud sync, system backups, or being sent by mistake as an attachment.
- **It does not defend against** an attacker who is already logged into the same machine under the same user account. Such an attacker can read this machine's hardware identifier and obtain the derivation parameters from the public source code, thereby recomputing the decryption key offline. This scheme also **does not defend against runtime process-memory reads**.

In short, this scheme narrows the exposure of plain-text keys from "anyone who gets hold of the file" to "someone who can execute code as you on this machine".

### Log location (for troubleshooting)

Application logs are written by tauri-plugin-log to the system log directory:

| Platform | Path |
|----------|------|
| macOS | `~/Library/Logs/com.hajifish.llm-token-monitor/` |
| Windows | `%APPDATA%/com.hajifish.llm-token-monitor/logs/` |
| Linux | `~/.local/share/com.hajifish.llm-token-monitor/logs/` |

> The logs contain no key material, so you can safely attach them when reporting an issue.

## Development

### Prerequisites

- [Node.js](https://nodejs.org/) v18+
- [Rust](https://www.rust-lang.org/tools/install) stable toolchain
- [Tauri system dependencies](https://v2.tauri.app/start/prerequisites/)

### Quick Start

```bash
# 1. Clone the repository
git clone https://github.com/hajifish/Local-LLM-Token-Usage-Monitor-Desktop.git
cd Local-LLM-Token-Usage-Monitor-Desktop

# 2. Install frontend dependencies
npm install

# 3. Run in development mode (with hot reload)
npm run tauri dev
```

### Building for Production

```bash
npm run tauri build
```

Built artifacts will be located in `src-tauri/target/release/bundle/`.
